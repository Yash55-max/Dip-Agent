Endpoint Data Leakage Prevention Agent

A hierarchical multi-agent monitor for Windows that watches per-process CPU, RAM, memory, and network behavior, scores exfiltration risk, and terminates high-confidence threats — while refusing, by design, to ever kill core system or security software.

TARGET OS: WINDOWS LANGUAGE: PYTHON STATUS: CORE LOGIC BUILT & TESTED · AGENTS DESIGNED, NOT BUILT

01Overview

This document describes a prototype data-leakage-prevention system: a main orchestrator agent supervising four specialized monitor agents, each watching one resource signal, scoring risk, and reporting up for a kill decision.

Read this before anything else: the system described below mixes code that exists and is tested with components that are designed on paper only. Every diagram and section below is labeled Built / Designed / Gap so it's clear which is which. Section 8 has the full breakdown.

The original concept (admin-managed whitelist gating disk access, four LLM sub-agents reporting to a main orchestrator that terminates flagged processes) is, at the architecture level, similar in shape to commercial endpoint DLP / EDR products (Teramind, Varonis, CrowdStrike). Those products watch user behavior across broader channels (USB, email, cloud upload) and use proprietary ML; this prototype is narrower in scope — Windows process-resource telemetry only — and currently uses explicit rules rather than a trained model where the design calls for one.

02Architecture

A main orchestrator process supervises four monitor agents. Each agent watches one signal, scores it independently, and reports a structured assessment upward. The orchestrator combines reports per-process, applies a final protected-process veto, and acts.

fig 1 — agent hierarchy and data flow. cyan = reports up. red = kill path, gated by the green veto box.

Main Agent (Orchestrator) Designed

Spawns and supervises the four monitor agents, collects per-process SignalReports, calls the risk engine, applies the protected-process veto, and executes (or refuses) termination. Process supervision and the OS-level kill call are not yet built — these need a real Windows process to implement and verify.

Risk Engine Built

Pure Python, no OS dependency. Aggregates signal reports into a weighted, time-decaying risk score per process, decides kill eligibility, and is the seam where a trained model will eventually replace rule-based scoring. 12/12 unit tests passing.

03Technology Stack

What each piece runs on, and why — including the parts not yet implemented.

Core logicBuilt
Python 3.12, stdlib only (dataclasses, enum)

No OS dependency by design — keeps the decision logic testable without a Windows machine, and portable if the agent layer ever needs to target macOS/Linux too.

Process telemetryDesigned
psutil

Cross-platform process/CPU/RAM inspection. Confirmed available in this environment, not yet confirmed against real Windows process behavior — per-process network attribution in particular needs verification.

Windows-native APIsDesigned
pywin32

Needed for service registration, privilege handling, and anything psutil doesn't expose (e.g. precise executable path / signature verification for the protected-process check).

Network attributionGap
ETW (Event Tracing for Windows) — likely needed

Per-process bandwidth and destination IP are not cleanly exposed by psutil alone. ETW is the realistic path to accurate per-process network data on Windows; this adds real complexity not yet scoped in detail.

Detection modelGap
Rule-based now → open-source model later

No labeled training data exists yet. The plan is to run the rule-based engine in production first, log its decisions and corrections, and use that log as training data for a future classifier — not to train a model on zero data today.

DeploymentGap
Windows Service (planned)

Running as a visible console app means any malicious process can see and kill the monitor before it acts. Service-mode deployment is necessary for the self-protection requirement, not yet implemented.

06Admin Whitelist / Blacklist Designed, not built

Per the original design: the admin maintains a list of trusted applications. Installed software is scanned and classified into a whitelist or blacklist; blacklisted applications are denied disk access.

ClassificationEffect on risk scoreEffect on disk access
WhitelistedScore multiplied ×0.2 — strongly dampenedUnrestricted
UnclassifiedNo adjustment — scored on signals aloneUnrestricted (default)
BlacklistedScore +0.5 flat additionDenied — see gap below

Note: full per-app disk-access blocking on Windows realistically requires either a kernel-mode minifilter driver (heavy: C/C++, code-signing, real driver-dev expertise) or a lighter approximation using NTFS ACLs and process termination. The lighter approximation is the realistic starting point for a prototype — this is flagged again under Challenges below.

07Challenges

Engineering obstacles specific to this design, independent of security risk (see next section for that).

Per-process network attribution on Windows is not trivialHigh

psutil exposes open connections per process but not clean, sustained per-process bandwidth or reliable destination-reputation data. Accurate values likely require ETW or a kernel-level network filter — both substantially more complex than the rest of the stack.

No labeled data exists for the planned modelHigh

The original design calls for training an open-source model on task-manager data. There is currently no dataset of labeled malicious vs. benign process behavior to train on — it has to be generated by running the rule-based system first and logging outcomes, which takes real operating time before any model work can start.

False positives have real cost, not just annoyanceHigh

CPU/RAM/Memory spikes are extremely common during legitimate work (compiling, gaming, antivirus scans, backups). A kill policy that's too aggressive erodes trust in the tool fast, or worse, disables legitimate software the user depends on.

Per-app disk-access blocking is a much bigger build than it soundsMedium

True OS-level enforcement needs a minifilter driver. That's a different skillset and a much longer build than the agent/orchestrator layer — worth scoping as a separate phase, not folded silently into "the app."

Privilege requirements limit how the tool can runMedium

Reading other users' process data and terminating processes needs elevated/admin privileges on Windows. The tool can't quietly run at standard-user level; this has UX and deployment implications (UAC prompts, service installation).

Threshold tuning has no shortcutLow

The numeric thresholds in the risk engine are reasonable starting points, not validated values. They need real-world tuning against actual usage on the target machine before they can be trusted.

08Security Concerns

Risks specific to the fact that this tool has kill authority and runs with elevated privileges. These are distinct from general engineering challenges — getting these wrong makes the machine less safe, not just less accurate.

The DLP agent itself is a kill target High

Real exfiltration malware can check the process list and kill the monitor before it acts, especially if it runs as a visible console process under a normal user account.

Mitigation (designed, not built): run as a Windows service under a protected account; sub-agents and orchestrator watch each other and restart on unexpected death; an unexpected agent death is itself logged as a suspicious event.
Kill authority is a privilege-escalation target High

The orchestrator needs elevated rights to terminate arbitrary processes. If the DLP tool itself is compromised, an attacker gains a SYSTEM-level process killer.

Mitigation (designed, not built): scope elevation to only the kill action where possible; write kill actions to a log location the agent process itself cannot modify.
Process-name spoofing of protected software High — mitigated

Malware naming itself MsMpEng.exe or svchost.exe could otherwise inherit protection meant for the real thing.

Mitigation (built & tested): protection for commonly-spoofed names requires executable-path verification against the expected install directory. Unverifiable or mismatched paths are treated as NOT protected and as elevated suspicion — confirmed in test_masquerading_fake_defender_not_protected_and_escalated.
IPC between agents is unauthenticated Medium

Whatever channel sub-agents use to report to the orchestrator (named pipes, sockets) needs to verify reports actually come from the legitimate sibling agent, or a malicious process could spoof an "all clear."

Status: not yet designed in detail — flagged as a requirement for the agent-layer build.
Killing security software disables real protection Medium — mitigated

A false-positive kill of antivirus/EDR is worse than doing nothing — it leaves the user believing they're protected when they aren't.

Mitigation (built & tested): known AV/EDR process names are in the protected registry and vetoed unconditionally, confirmed in test_real_av_vendor_no_path_check_needed and the Defender test above. The list is a starting set and not exhaustive — needs expansion to match the actual AV in use before relying on it.
Whitelist/config files can be tampered with Medium

If a malicious process can write to the whitelist, it can add itself and bypass detection entirely.

Status: not yet designed — needs integrity verification (hash/signature) on config files, deferred per project sequencing.
